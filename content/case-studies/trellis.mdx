<CaseSection id="customer">

14 Acres Vineyard & Winery is a working winery and tasting room in Ridgefield, Washington. Its wine club has about **800 members** who are charged on a schedule, and every charge goes through the **Clover POS** the tasting room already uses.

Staff manage members in Trellis’s admin; members get their own pages.

The wine club manager runs club billing quarterly, but every staff member uses the wine club software to check which customers are club members and to make sure their details and card on file are accurate.

</CaseSection>

<CaseSection id="discovery">

**What they asked for:** a replacement for the winery’s club billing vendor, which was discontinued.

**The real problem:** whatever replaced it had to be trustworthy with money from day one, charge through the winery’s existing Clover account, and not require a rewrite to serve other wineries later.

**What went wrong with the old software:** it was very buggy, with many problems and critical security issues. There were so many issues that staff stopped using it.

</CaseSection>

<CaseSection id="constraints">

Every charge has to go through Clover, since that’s the POS the tasting room already uses. The money side needed the most care. About 800 members get billed on a schedule, and jobs sometimes fail and retry, so I had to make sure a retry could never charge anyone twice.

I’m aiming for the first live member charges in January 2027. On budget, the goal is to keep it as cheap as I can without ending up with software nobody can rely on. I design it and direct an AI-assisted build, and I review and test every change before it merges.

</CaseSection>

Staff manage members in the Next.js app, while workers on Render handle the charge schedule and the calls to Clover. I put a winery ID on every table and turned on Postgres row-level security, so one winery can’t see another winery’s data.

<Decisions>
  <Decision title="No double charges">
    Every Clover payment gets an idempotency key. If a job retries, Clover sees the same key and won’t bill the member a second time.
  </Decision>
  <Decision title="Multi-tenant from day one">
    I added tenant IDs and row-level security from the start. I’d rather do it now than rewrite everything when another winery wants to use Trellis.
  </Decision>
  <Decision title="CI on every push">
    Every push runs through GitHub Actions: lint, tests, and a secret scan. Nothing merges until those pass.
  </Decision>
</Decisions>

<CaseSection id="broke">

Trellis isn’t live yet, so nothing has broken in production. One thing I changed from the original build plan: the admin now listens for database changes and updates on its own.

You can see it with card updates. Staff can send a member a secure link to update their card on file without the member having to log in. As the email goes from queued to delivered to opened, each status gets saved in the database and shows up in the admin right away, no reload needed.

</CaseSection>
