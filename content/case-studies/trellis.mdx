<CaseSection id="customer">

14 Acres Vineyard & Winery is a working winery and tasting room in Ridgefield, Washington. Its wine club has about **800 members** who are charged on a schedule, and every charge goes through the **Clover POS** the tasting room already uses.

Staff manage members in Trellis’s admin; members get their own pages.

The wine club manager runs club billing quarterly, but every staff member uses the wine club software: to check which customers are club members, and to make sure their details and card on file are accurate.

</CaseSection>

<CaseSection id="discovery">

**What they asked for:** a replacement for the winery’s club billing vendor, which was discontinued.

**The real problem:** whatever replaced it had to be trustworthy with money from day one, charge through the Clover account the winery already runs on, and not need a rewrite to serve other wineries later.

**What went wrong with the old software:** it was very buggy, with many problems and critical security issues. There were so many issues that staff stopped using it.

</CaseSection>

<CaseSection id="constraints">

- **Existing systems:** every charge has to go through Clover, the POS the tasting room already uses.
- **Money:** about 800 members are billed on a schedule, so a retried job can never charge someone twice.
- **Timeline:** first live member charges are planned for January 2027.
- **Budget:** as cheap as possible while still producing viable software.
- **How it’s built:** I design and direct an AI-assisted build, and review and test every change.

</CaseSection>

Staff manage members in the Next.js app. Workers on Render run the charge schedule and call Clover. Every table carries a winery ID, and Postgres row-level security means one winery can never read another’s data.

<Decisions>
  <Decision title="No double charges">
    Each Clover payment carries an idempotency key, so a retried job can’t bill a member twice.
  </Decision>
  <Decision title="Multi-tenant from day one">
    Tenant IDs and row-level security now, so selling to other wineries doesn’t mean a rewrite.
  </Decision>
  <Decision title="CI on every push">
    GitHub Actions runs lint, tests and a secret scan before anything merges.
  </Decision>
</Decisions>

<CaseSection id="broke">

Trellis isn’t live yet, so nothing has broken in production. One thing I changed from the original build plan: the admin now listens for changes in the database and updates on its own.

For example, staff can email a member a secure link to update their card on file without logging in. As that email moves from queued to delivered to opened, the database records each status, and the admin shows it right away, without a reload.
